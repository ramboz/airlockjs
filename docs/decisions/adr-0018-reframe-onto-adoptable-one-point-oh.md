# ADR-0018: Reframe: 1.0 means adoptable with confirmed parity (re-baselining the release ladder)

## Status

Proposed (2026-09-07)

## Context

The owner moved airlock's definition of 1.0 on 2026-09-05 — from "the public API is frozen" to "a developer can rewire a real site's TBT-dominant tags onto airlock with confirmed parity" — and the corpus still encodes the old definition as settled truth. This is a **reframe** (jig spec 067 / ADR-0024 in jig): a load-bearing *product-positioning* reference changed from outside the system, so the consistency machinery would otherwise carry the dead premise forward. This keystone ADR makes the new reference authoritative, names what it supersedes, and carries the re-baselining manifest + coverage floor that a session executes.

**The dead premise** — *1.0 = the API pin*. It was encoded as settled truth by: the MVP6 release plan (`docs/releases/mvp6.md`, titled "Adoption & 1.0 Readiness", whose Include row 3 treats the "1.0 API stability pin" as the adoption-readiness deliverable and defers "the v1.0.0 version-bump/tag/dist release cut" as its follow-on); [ADR-0017](adr-0017-airlock-1-0-api-contract.md)'s title and its "FROZEN at 1.0" labels (mirrored verbatim into `contracts/README.md`, `contracts/{capability,connector,seams}.d.ts`, `docs/architecture.md` § Contract surfaces, and the root `README.md`'s "Pre-1.0 … until the 1.0 API-stability pin"); spec 037's title ("The 1.0 API pin (MVP6 capstone)"); and — the other half of the premise — [R-007](../research/R-007-real-prod-stack-breadth.md)'s self-description as "**deliberately beyond current scope** — a north-star benchmark", i.e. the real production stack was explicitly *not* the bar.

**The new reference (owner decision, 2026-09-05; ratified with the Segment clarification 2026-09-07).** A version 1.0 of airlock is one a developer with automation skills can **adopt on an intuit-class site** — an AEM EDS migration whose Lighthouse score collapses (100 → ~60) under a Tealium/GTM/Launch container — by **rewiring the TBT-dominant *generic* vendor tags (GA4, Meta Pixel, Google Ads, Floodlight) from the container to airlock, with beacon-level parity confirmed by a vendor-generic parity harness**, through a documented, scripted path. The evidence behind the bar: on the reference site, the three ad/marketing runtimes (Meta `fbevents.js`, Google Ads `gtag.js`, Floodlight) account for roughly two-thirds of martech TBT (the owner's attribution report, 2026-09-05: 601.5 ms → 204 ms with those three removed), and all three are beacon-shaped — exactly the wire-protocol/pixel archetype airlock already proves for GA4. Without that rewire-with-parity, the owner expects no adoption: an API freeze is necessary but is not what makes airlock adoptable.

**What is *not* moving.** ADR-0017's *contract* — the five frozen surfaces plus the adopter boot layer, the experimental carve-out, its three rulings, and its break rule — stands unchanged. Only the *label* "1.0" decouples from it: the frozen surface is **the stable core**, effective since spec 037-01 landed, and 1.0 ships *on* it. That is why this is a re-read of ADR-0017, not a supersession.

## Decision Options Considered

### Option A: Keep 1.0 = the API pin; cut v1.0.0 now (the deferred follow-on in mvp6.md / ADR-0017 OQ3)
- **Pros:** honours the recorded plan; the stable core is genuinely frozen and guarded, so a 1.0 label is defensible on API grounds.
- **Cons:** ships a "1.0" that no real site can adopt for its actual problem (the TBT-dominant tags are unsupported: no Google Ads / Floodlight connector, Meta Pixel identity/POST deferred, no parity evidence for any vendor). The owner's stated adoption bar is unmet; the label would mislead the exact audience 1.0 exists for. Rejected.

### Option B: Supersede ADR-0017 with a new "1.0 contract" ADR
- **Pros:** one clean decision record for "what 1.0 is".
- **Cons:** ADR-0017's *content* is not wrong — the frozen surface, the carve-out, the rulings and the break rule all survive intact; superseding it would retire a correct contract and force every "FROZEN (ADR-0017)" reference in the corpus to re-point. Only the label moved. Over-built for a re-read. Rejected.

### Option C: Patch the release plans only (retitle MVP6, add MVP8/9) and leave the corpus as is
- **Pros:** cheapest; the slate reads right.
- **Cons:** the corpus keeps saying "FROZEN at 1.0" / "the 1.0 pin" / "beyond scope" — the next session to draft against the contracts or R-007 inherits the dead premise under fresh authority (the exact failure a reframe exists to prevent). Rejected.

### Option D (chosen): A keystone reframe-ADR — new reference authoritative, old premise named + dispositioned artifact-by-artifact, ADR-0017 re-read not superseded
- **Pros:** the new bar becomes an accepted decision the corpus can cite; every artifact that encoded the old premise gets a deliberate disposition (no silent carry-forward); the correct contract survives untouched; the ladder and versioning are re-baselined in one place.
- **Cons:** a corpus-wide edit set (mostly relabels) and a manifest that is only as good as its read — mitigated by the two-level coverage floor below, confirmed at this ADR's frame-critique gate.

## Recommended Decision

Adopt **Option D**. As of **2026-09-05** the authoritative definition of airlock 1.0 is:

> **1.0 = adoptable with confirmed parity.** A developer with automation skills — **working with the container owner** (the rewire is two-party, below) — can rewire an intuit-class site's TBT-dominant *generic* vendor tags — **GA4, Meta Pixel, Google Ads, Floodlight** — from its tag-manager container (Tealium / GTM / Launch) to airlock, with **parity at the vendor boundary confirmed by the parity harness and the vendor consoles**, the TBT/CWV win **measured** on a proper before/after (the container as-is vs the container with those tags natively excluded + airlock), through a **documented, scripted adoption path**. [R-007](../research/R-007-real-prod-stack-breadth.md) — the classified real production stack — is **the 1.0 benchmark**, promoted from "north-star, beyond scope".

**The rewire is two-party, and the after-arm is the container owner's to produce (load-bearing).** On the reference site the container is **not** the developer's: the customer-owned Tealium profile (`ies-erp`) owns tag delivery, the OneTrust→category mapping and Consent Mode v2 enforcement, and page code is told *not* to add loaders for profile-owned vendors (`intuit-erp/MARTECH.md` § Load sequence, § Consent ownership, § Profile-owned integrations). The site-side lab allowlist cannot produce the after-arm either — the container still downloads and initialises every active tag template (`MARTECH.md` § Tag-template load limitation: "true per-tag performance isolation" needs native load-rule exclusion on a lab version of the profile). Therefore: **(i)** the 1.0 proof's *before* arm is the container as shipped and its *after* arm is **the container with the four tags natively excluded + airlock** — which is **not** what the spec-036 harness measures (`?airlock=1` = site vs site + airlock, i.e. airlock's *own* cost; that stays MVP6's proof and is reused as the CWV *instrument*, with MVP9 adding the rewire arms and *win* semantics, E12). **The after-arm must be same-host and query-gated, not a dev profile on another host**: on the reference site the Tealium environment is hostname-selected (`MARTECH.md` § Environment — the prod profile exists only on `*.intuit.com`; other hosts map to `dev`, where the OneTrust CDN may be blocked and `utag.js` then never loads), so "a lab profile" would reproduce exactly the cross-deployment fixed-offset confound spec 036 demoted to a band-withheld fallback. The profile's own documented mechanism avoids it: **querystring-gated native filter rules** (`tealium-tags` as a Querystring data source, one filter rule per tag UID, inert when the parameter is absent — `MARTECH.md` § Tag-template load limitation) **published to the production profile**, so both arms are the same URL on the same host, differing only by the query gate — the 036 design. **(ii)** the scripted adoption path (E8) is two-sided — the developer's side (config, boot, captures, the harness run) and a **container-owner checklist** (publish the query-gated native exclusion for the rewired tags to the production profile; exclude them outright for the live window; read access to — or exported reports from — Meta Events Manager, Google Ads, CM360 and GA4 for the console leg); **(iii)** the owner of this repo is the EDS developer on the reference site, **not** its container owner — that cooperation is a named assumption with its own kill criterion below, not a given.

**The console leg has two levels, and only one is lab-observable.** *Event-level receipt* — each vendor's diagnostic surface confirms the rewired events arrive with the expected fields (Meta Events Manager / Test Events with its match-quality signal; GA4 DebugView + realtime; Google Ads conversion diagnostics; Floodlight verification) — is observable on a **lab profile with tester traffic**. *Attribution* — view-through, cross-device, CM360 linkage — is an aggregate, delayed, real-visitor property observable **only under live traffic**, which on the reference site means the four tags natively excluded in the **production** profile plus airlock, over a **live comparison window** (sequential, or a cohort split). **Both levels are in the 1.0 release-check**: the lab level is what the developer can drive; the live window is the container owner's production ask, named as such in the assumption and kill criterion below. If the live window cannot be obtained, 1.0 is not quietly cut on the lab level — the owner re-decides (an explicitly re-decided event-level-only bar is a decision; an assumed one is the narrowing this ADR forbids). **The before-arm is the container as shipped in production, and the win is reported against two baselines.** On the reference site the shipped configuration is phase-split **off** — `?martech-phase-split=on` (which defers Floodlight and Google Ads to `delayed_ready`) is an *opt-in lab switch* for controlled traces, not the production default (`MARTECH.md` § Load sequence, § Environment). So the proof reports the rewire's CWV delta against **(1) the shipped container** (the adoption number) **and (2) the container's best available phased configuration** (the honest "what airlock buys beyond what the container can already do") — a win that exists only against (1) is disclosed as such, never presented as the whole story. The owner's 601.5 → 204 ms attribution figure is **reported, not repo-grounded**: the configuration it was measured under is not recorded here, so the 1.0 CWV win is re-measured on the rewire arms — and its *upper bound* is measured first, without the container owner, by R-010 (E11: the shipped page vs the same URL with the four vendor runtimes blocked via Lighthouse `blockedUrlPatterns`, on both configurations). **The CWV half has a threshold and a kill criterion of its own** (below): the after-arm must bring the reference page(s) into the CWV "good" band / back to the site's pre-martech Lighthouse band; a modest delta that leaves the container's *fixed* cost dominant (the `utag` core, every remaining template initialised in `PINIT`/`INIT`, the customer's own ECS chain, OneTrust — all outside 1.0's scope by R2) withholds 1.0 and sends the bar back to the owner.

**What "parity" means (load-bearing — defined here so it cannot be quietly widened later).** *Semantic parity at the vendor boundary*: the same events, carrying the same attribution-bearing fields (client/visitor ids, session, consent state, conversion labels + values), reach the vendor as they did from the container — confirmed by **(i) a per-vendor oracle** and **(ii) the vendor's console**. The oracle is a **same-protocol beacon diff** where airlock speaks the container's protocol (Meta Pixel GET; Floodlight / Google Ads pings) and a **semantic field-map** where airlock legitimately speaks a *different* vendor protocol — the grounded case is **GA4**: airlock's connector emits the server-side **Measurement Protocol** (`/mp/collect`, `connectors/ga4/map.js:81`; `contracts/ga4-mp.md`), while a container's GA4 tag loads `gtag.js` and emits `/g/collect` with a different encoding and field vocabulary. So the parity harness is **vendor-generic in shape** (capture → replay → oracle → report) with **per-protocol oracles**, and GA4 parity is **not** a confirmation step but the harness's first real test (see the ladder's MVP7 risk-first item, the Assumptions, and Kill criteria).

Two further properties of the definition, both load-bearing:

- **Transport is part of the vendor boundary, not just the beacon.** A container's Meta / Google Ads / Floodlight tag fires via `<img>` / `sendBeacon` / credentialed requests, so — on the browser cohort that still allows third-party cookies (Chrome's default) — every hit carries the vendor's cross-site cookie (`fr` on facebook.com, `IDE` on doubleclick.net), which is the identity behind Meta match quality, Google Ads view-through / cross-device conversions and CM360 attribution. airlock's egress is `fetch(url, { method, keepalive: true })` (`core/airlock.js:48–50`, default `mode: "cors"`, `credentials: "same-origin"`): cross-origin vendor hits carry **no** cookies and honour no `Set-Cookie` (grounded 2026-09-07: no `credentials` / `no-cors` handling exists in `core/`, `adapters/`, `connectors/`, or `contracts/` — `rg`; only rigs use it). A URL+params diff would therefore report parity while the vendor consoles diverge on the Chrome cohort. **Parity is measured on both cohorts** — third-party-cookies-allowed and -blocked (Safari/Firefox, where the container itself has no cross-site cookie) — and the harness **captures and replays the credential/cookie context of every hit**, so a transport-caused divergence is *visible*, never hidden inside a "same beacon" verdict. Whether airlock closes that divergence — a **purpose-gated credentialed transport** to declared endpoints (`mode: "no-cors"` + `credentials: "include"`, the exact transport of an `<img>` beacon; the chamber never sees cookie values, the browser's own jar attaches them; gated on the `ad_storage`-class purpose per ADR-0007; an *additive* `EgressRequest` field, so no stable-core break) — is a **security-boundary decision this ADR does not make**: it is Emergent E10, a follow-on ADR with its own frame-critique, decided in MVP7 *before* the harness oracle is specced. Silently accepting the Chrome-cohort gap by defining parity as "cookieless-comparable metrics only" is exactly the narrowing this ADR forbids.
- **The oracle is semantic, never raw URL equality.** Vendor hits carry nondeterministic fields (cache-busters, DSP-assigned ids, timestamps) — the reference site's own diff tool already refuses raw URL comparison for this reason (`intuit-erp/MARTECH.md` § Validation) — so every per-vendor oracle normalizes to the attribution-bearing field set before diffing.

### The rulings

- **R1 — ADR-0017 is re-read, not superseded.** Its frozen surface is **the stable core** (effective now); its experimental carve-out, three rulings, and prerequisite stand. Every "FROZEN at 1.0 (ADR-0017)" label in the corpus reads **"FROZEN — stable core (ADR-0017)"**; every "pre-1.0 / not frozen" label reads **"not frozen (experimental)"** — the fact is unchanged, only the tie to a release date is dropped. A change to the stable core still requires a superseding ADR. Because the codebase is pre-1.0, ADR-0017's "major-version break" cannot be literal until v1.0.0 exists (jumping to 1.0.0 in order to break the stable core would violate R4), so in the 0.x window a stable-core break is expressed as a **minor bump carrying the superseding ADR plus a CHANGELOG break notice**. This is honestly a **partial amendment of ADR-0017's "trust it across minor versions" consequence, confined to the pre-1.0 window** — carried in ADR-0017's amendment pointer (manifest) — and it lapses at v1.0.0, when the literal rule resumes. The promise that survives unchanged is *no silent change*: a stable-core break is never a refactor, always a named decision.
- **R2 — Customer-custom tags are validation-only, never release scope.** A customer's own tag logic — on the reference site, Intuit's **ECS / TrackStar / UX-Fabric** click-tracking chain (Tealium UID 26) and the 161-beacon golden sample it produces — is **never** a shipped connector, deliverable, or release gate. It may serve as a *local* validation input (a regression guard that a rewire left the untouched custom chain intact). Release scope names **generic vendors only**. Corollary: **Segment** (Twilio Segment, `analytics.js`, the HTTP tracking API) is a *generic* vendor and a legitimate connector target, but it is **not** on the 1.0 critical path — on the reference site the cost sits in the custom chain around it, not in Segment itself — so it moves to variable/later scope and R-007's host-vs-replace question stays open, unforced.
- **R3 — Parity is a co-equal success criterion.** The vision's implicit success criterion ("all three use cases land at ~zero CWV cost, on a before/after scoreboard") gains a second, co-equal half: **beacon-level parity with the container airlock replaces**, confirmed by the parity harness. CWV without parity is a demo; parity without CWV is a port.
- **R4 — Versioning.** The existing `MVPn ↔ v0.n.0` convention continues (MVP5 shipped as v0.5.0). **v1.0.0 is cut when MVP9's release-check passes — never by an API pin alone.** The deferred "v1.0.0 cut" follow-on of the pin is retired; MVP6 cuts **v0.6.0**.
- **R5 — Real-site inputs stay local and redacted.** The parity harness is the release deliverable; each real site supplies its own vendor-beacon captures as its oracle. Committed fixtures are synthetic/redacted (the standing "no live vendor identifiers" no-go; spec-013 redaction discipline); the reference site's captures are "LOCAL ONLY".

## Kill criteria

- **CWV (MVP7 R-010, then MVP9).** If R-010's upper bound — or MVP9's honest before/after against the shipped container — shows the rewire does **not** bring the reference page(s) into the CWV "good" band / back to the site's pre-martech Lighthouse band because the container's fixed cost dominates, 1.0 is withheld and the owner re-decides the bar (a wider rewire set, a different reference site, or an explicitly re-decided target). A parity pass plus a small number is never a 1.0.
- **GA4 (MVP7 risk-first).** If R-009 (a) shows MP-only egress **cannot** reach console-level parity — **or that MP is unacceptable for a public property on `api_secret`-exposure / bot-filtering grounds** (an adoption blocker no parity check sees) — the exits are, in order: **(a)** a second, *additive* gtag-protocol GA4 connector (`/g/collect` emitted off-thread; frozen surface 1, the MP schema, is untouched, so no stable-core break) if the spike shows the protocol is reproducible; else **(b)** the owner re-decides the bar. Never a redefinition of "parity" to fit what MP delivers.
- **Google Ads + Floodlight — protocol (MVP7, R-009 b/c).** If the lab spike shows the conversion pings **cannot** be reproduced from governed egress at all (protocol / Consent Mode semantics that require the vendor runtime on the page), the 1.0 rewire set does **not** silently shrink to the non-dominant pair: those two tags carry most of the cited two-thirds of TBT, so "TBT-dominant tags rewired" would be false — the owner re-decides the bar, recorded by a follow-on ADR.
- **Google Ads + Floodlight + Meta — transport (MVP7, E10).** If E10 is **rejected** on security grounds, a missing `fr` / `IDE` on the cookies-allowed cohort is *by definition* a parity miss there (visitor ids are attribution-bearing; the definition forbids absorbing it) — the owner re-decides the bar explicitly (a documented, owner-accepted cohort gap is a *re-decided* bar, never an absorbed footnote).
- **Attribution (MVP9 only).** View-through, cross-device and CM360 attribution are observable only in the vendor consoles under live traffic. If the console leg shows a divergence the lab could not see, 1.0 is withheld and the owner re-decides — the lab spike is not allowed to stand in for this leg.
- **Container-owner cooperation (MVP9).** If, within the ladder's horizon, the reference site's container owner does not provide the after-arm (native exclusion on a lab profile), console read access / reports, **and a production exclusion for a live comparison window** — or no other intuit-class site with a cooperating owner is available — 1.0 is **not** cut on the 036 site-vs-site+airlock instrument, on synthetic evidence, or on the lab-level console check alone; the ladder pauses at v0.9.0 and the owner re-decides the bar (another site, or an explicitly re-decided bar — e.g. event-level receipt as the 1.0 gate with attribution carried as a named post-cut residual). Passing the oracle alone never substitutes for the console leg, and the lab level never silently substitutes for the live window.
