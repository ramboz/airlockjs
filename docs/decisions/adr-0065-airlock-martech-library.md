## Summary

Adobe's EDS sites run Adobe Experience Platform Web SDK (Alloy) through the `aem-martech` library, which loads Alloy on the main thread and calls a page-global `window.alloy`. Airlock runs Alloy in a chamber and has no such global. This ADR adds a new Airlock-native library, `adapters/eds/martech.js`, with the same exports as `aem-martech` that talk to the `bootAlloy` handle directly. A site swaps one import and keeps its `initMartech` / `martechEager` / `martechLazy` / `martechDelayed` calls. The library never reads or writes `window.alloy` and never loads `alloy.min.js` on the main thread. It also loads no ACDL and installs no `window.adobeDataLayer` by default: the data layer is Airlock's own generic mechanism, shaped like `airlock.push({ event, ...params })` and `airlock.getState()`, and `adobeDataLayer` is an opt-in migration proxy, not a best practice. The main tradeoff: a site that calls `window.alloy` directly gets a loud failure instead of a shim, a site that relied on ACDL's function pushes or listeners gets a diagnostic, and the library stays source-compatible with `aem-martech` at the export level only.

## Context

- Today's product path is the 064-21 wrapper (`adapters/eds/alloy-bridge.js`, `createAlloyCommandBridge`): an `alloy(command, options)` function that maps stock commands onto the handle. The stock `aem-martech` can only use it through a test-only shim (`rig/alloy-queue-shim.mjs`) that installs `window.alloy`, because `aem-martech` hard-codes `await import('./alloy.min.js')` and calls `window[instanceName]`. The shipped adapter has no global, by design (ADR-0063; 064-21 Findings).
- `aem-martech` is pinned at `adobe-rnd/aem-martech` 1aa3dee3, `src/index.js` (Apache-2.0). Its 14 exports: `DEFAULT_CONFIG`, `sendEvent`, `sendAnalyticsEvent`, `pushToDataLayer`, `pushEventToDataLayer`, `updateUserConsent`, `initMartech`, `initRumTracking`, `isPersonalizationEnabled`, `getPersonalizationForView`, `applyPersonalization`, `martechEager`, `martechLazy`, `martechDelayed`. It also loads ACDL (the Adobe Client Data Layer, `acdl.min.js`) on the main thread, registers an `adobeDataLayer:event` listener, reads `getState()` for `includeDataLayerState`, and pushes `data-block-data-layer` blocks. ACDL runs page callbacks inside the push, which is what Airlock's capture layer (`contracts/push-api.md`, AD-2, AD-3) exists to avoid: the main thread captures, enqueues and folds a cheap projection, and interpretation happens elsewhere.
- The handle already has what the library needs for most calls: `push` (every stock `sendEvent`, with per-call `decisionScopes` and `personalization`), `setAdobeConsent` (ADR-0064), `applyPropositions` (064-20), `command` (ADR-0063's five commands), the first-push-after-`applyResponse` path (064-29), and `bootAlloy` boot options including `thirdPartyCookiesEnabled` (064-30).
- Three things the handle does not give today, found by the 064-21 differential and parked in slice 064-31: `push` returns nothing, while `aem-martech`'s eager phase reads `propositions` from what `sendEvent` resolves with; `handle.applyPropositions` takes propositions but not a `viewName`; stock Alloy 2.31.1 accepts `viewName` only alongside non-empty `propositions` (`createApplyPropositions`, read from the pinned tag source; amended 2026-11-22, see the note at the end of this section); and `setAdobeConsent` does not settle with Alloy's outcome (ADR-0064 point 9).
- The seal decides egress from the live consent vector (ADR-0007, ADR-0062). The chamber is untrusted.

## Decision Options Considered

### Where the library lives

#### Option A: a module in `adapters/eds/` (recommended)
`adapters/eds/martech.js`, built into the same `AirlockEds` bundle and distributed by the same git subtree (ADR-0015) as the rest of the adapter.
- **Pros:** The library's only dependency is the `bootAlloy` handle, which lives in the same adapter. One distribution path, one version, one test setup. A site that already takes `adapters/eds/` gets it with no extra package.
- **Cons:** It grows the EDS adapter surface. The ADR-0017 frozen API contract does not list it, so it ships as experimental until a later ADR freezes it.

#### Option B: a separate package
- **Pros:** Its own version and release cadence, and a name sites could install in place of `aem-martech`.
- **Cons:** A second distribution channel for a library that cannot work without the adapter's private handle shape. ADR-0015 chose git subtree for EDS on purpose (no npm install in a buildless site). A package would have to track the adapter version one to one anyway. Rejected for now; nothing in Option A prevents extracting it later.

### How the library reaches Alloy

#### Option A: call the `bootAlloy` handle directly (recommended)
The library's `sendEvent` runs the page's hook on the main thread, then calls the handle. No `alloy(command, options)` function exists in it.
- **Pros:** No global and no command-name switch. Each export maps to a typed handle entry point the seal already governs.
- **Cons:** It needs the three handle additions in the Context (they are slice 069-01).

#### Option B: keep the wrapper and install it as `window.alloy`
- **Pros:** `aem-martech` itself would run unchanged.
- **Cons:** A shipped global that any page script can call is a capability leak the owner declined on 2026-11-20. Rejected.

### Where the data-layer behavior lives (the owner picked Option A on 2026-11-21)

The behavior in question: the state merge behind `includeDataLayerState`, the mapping of data-layer events to `sendAnalyticsEvent` arguments, and the `data-block-data-layer` blocks. The standard surface is Airlock's generic data layer (`airlock.push({ event, ...params })`, `airlock.getState(path)`, `contracts/push-api.md`, AD-2, AD-3), not `adobeDataLayer`. Page functions (`shouldProcessEvent`, `onBeforeEventSend`) cannot cross the airlock in any option, so a main-thread consumer stays in all of them.

#### Option A: behavior on the main thread in a pure adapter module (picked)
`adapters/eds/martech-datalayer.js`, a pure, dependency-free module: `push` validates and appends (O(1) in the state size, no page code), the state folds lazily, and a consumer drains events in a separate task to the library's `sendAnalyticsEvent`. It uses core's envelope and API shape and needs no `core/` change (the gap table in point 5 says why).
- **Pros:** No `core/` change and no chamber-to-chamber path. The synchronous `getState()` read stays correct. The reducer is pure, so it can move into a chamber later. One module to prove against real ACDL 3.0.1 in the differential.
- **Cons:** The fold and the event mapping run on the main thread (in a separate task, and at read or send time), and each state-carrying send costs O(state size). A step short of "all interpretation behind the airlock".

#### Option B: designed through a chamber
A data-layer chamber receives every captured push, holds the state and maps events, and feeds the Alloy chamber.
- **Pros:** The closest fit to the vision: the main thread only captures and enqueues, and the state and the mapping live off-thread.
- **Cons:** No chamber-to-chamber path exists, so it needs a `core/` change (vendor-neutral, and named in a later ADR) or it puts a generic data layer inside the vendor Alloy chamber, which breaks the one-connector-per-chamber rule. The synchronous `getState()` read and the page functions still need a main-thread projection and drain step, so the main thread keeps most of the work. It also splits one logical Alloy send across two chambers, and the state would still have to reach the Alloy chamber in `xdm`.

#### Option C: keep ACDL, loaded as `aem-martech` does (rejected)
- **Cons:** The owner declined it: "not taking ACDL as is". ACDL runs page callbacks inside the push (INP risk on the interaction path), adds a main-thread file, and its listener model is the thing the capture layer replaced.

The owner picked Option A, with the reducer kept pure so Option B stays open: it needs no `core/` change, keeps the main-thread cost bounded and measured, and moving the reducer into a chamber later is a contained change.

## Recommended Decision

Adopt Option A in the first two tables, and Option A of the data-layer table pending the owner's choice. The mechanics:

1. **Shape.** `adapters/eds/martech.js` exports a factory, `createMartech(handle?, opts?)`, and the 14 `aem-martech` names plus one extra, `getAirlockHandle`, as functions bound to a default instance (module state, as in `aem-martech`: `initMartech` may run once and the other calls assert it ran). The factory exists so tests and sites can run several isolated instances without module state. The default instance is created by `initMartech`. The library is written against the pinned API surface and its observable behavior; where a small piece is a structural re-expression of `aem-martech` source (the consent-object build, the proposition-apply loop, the data-layer state merge), the file keeps the Apache-2.0 notice for `adobe-rnd/aem-martech` and the repository's third-party notice names it, as the license requires.

2. **The export map.** Each of the 14 exports, plus the extra:

It boots the chamber with `bootAlloy`, from the boot options in `martechConfig.airlock`, an allowlist of `bundleUrl` and `workerUrl` only (any other key, notably `consent` and `consentHold`, is rejected with a plain Error at `initMartech`: the first would grant before the page's consent call, the second would leave the consent reference unset so `updateUserConsent` silently does nothing), or reuses a handle passed as `martechConfig.handle`. `airlock` and `handle` are library-only `martechConfig` keys, beyond `DEFAULT_CONFIG`. 3. **No page global.** The library never reads or writes `window.alloy`, `window.__alloyNS` or any `window[alloyInstanceName]`, and never imports `alloy.min.js` on the main thread (Alloy runs in the chamber, loaded from the adapter's `bundleUrl`). `alloyInstanceName` is inert; setting it to anything but `"alloy"` is diagnosed `unsupported-option`. `dataLayerInstanceName` is inert by default (the library writes no data-layer global); it is only the proxy's default `instanceName`, and there it is rejected with a plain Error when it equals `alloy`, `__alloyNS` or the `alloyInstanceName` value, since the proxy would then write a forbidden global. A site that today calls `window.alloy(...)` directly fails loudly (the global does not exist, so the call throws): no shim and no detection, since detecting it would mean reading the global. It is told in three places: the library's header, `docs/architecture.md`, and a migration note in the slice Findings that maps each stock `alloy("command")` call to `getAirlockHandle()` (`sendEvent` to `sendEvent`/`sendAnalyticsEvent`, `setConsent` to `updateUserConsent`, `applyPropositions`, `getIdentity` and the rest to `command`). Calls with no handle counterpart are out of scope and listed there.

4. **The hook runs on the main thread.** `onBeforeEventSend` (the library's own and the page's) is a function, so it cannot cross the airlock; it runs where the page's code is, before the event is enqueued, exactly as the wrapper does today. The event the chamber sees is the hook's output. A throwing page hook drops the event and, since 069-01, rejects the `sendEvent` promise, as stock does (064-31 AC5 moves to 069-01). `shouldProcessEvent` is the same kind of function and stays on the main thread too, but it runs in the data layer's drain step after the push returns, not inside the push (point 5).

5. **The data layer.** The library loads no ACDL (no `dataLayerUrl`, no `acdl.min.js` request) and installs no `window.adobeDataLayer` by default. The standard is Airlock's generic data layer, built in slice 069-02 as `adapters/eds/martech-datalayer.js` (Option A, the owner's pick):
   - **The generic mechanism.** It has the shape of what exists: `push({ event, ...params })` and `getState(path)` as in `contracts/push-api.md`, with the same envelope guard (a malformed push is dropped with a warning, never thrown), plus state pushes with no `event` key (below). `push` validates a plain data object (no accessors, no `Proxy`, bounded depth, so no page code runs and no cycle overflows) and appends it to a queue: O(1) in the state size, no merge on the push path. The state folds lazily, at `getState()`, at send when `includeDataLayerState` needs it, or in the drain, and is cached until the next push and updated in place, so a reference from `getState()` stays live (own keys, `__proto__`, `constructor` and `prototype` skipped, values copied). The library's `pushToDataLayer`, `pushEventToDataLayer`, `includeDataLayerState` and the event mapping build on it: an event push maps, in a drain in a separate task, to `sendAnalyticsEvent({ eventType, ...xdm }, data, configOverrides)` taking only those four keys, attached in the lazy phase and only when `analytics` is true (earlier events are held and replayed in order); the send-time state merge hands the hook a copy and costs O(state size) per send. `data-block-data-layer` blocks are scanned once in `martechLazy` and pushed through it with stock's id assignment.
   - **Gaps between the generic mechanism and Adobe parity, and the fix for each.** The fix for all four is an adapter-level module; no `core/` change is needed, and phase 2's `core/` diff must be empty.

     | Gap | Core today | Fix (recommended: adapter-level) |
     |---|---|---|
     | State pushes with no `event` key | `airlock.push` drops a push without `event` (`core/airlock.js` envelope guard). | The adapter's data layer accepts them and folds them into its own state (`push-api.md` keeps the guard for core). The alternative, a vendor-neutral `core/` change letting `push` carry state, is rejected for now: it widens the pinned envelope for one adapter. |
     | Merged state vs core's per-event projection | Core's projection is `projection[type] = descriptor`, last write per event type. Stock ACDL's `getState()` is a deep merge. | The adapter owns the deep-merge reducer, proven equal to ACDL 3.0.1's `getState()` (069-02 AC3). Core's projection stays as it is. |
     | A main-thread consumer, so `shouldProcessEvent` and `onBeforeEventSend` run in the drain | Core has no subscribe surface, by design. | The adapter's drain is the consumer: one callback (`onEvent`) the library passes. A core `subscribe` is rejected: it would add the page-callback surface AD-2 avoids. |
     | Denylist coverage (ADR-0012) | The denylist strips events that go through core's standard dispatch; alloy's wrapped-SDK input seam is a named gap (`push-api.md`, refinement-todo). | The adapter's data layer is not core's dispatch, so it does not inherit the denylist, and the Alloy path is the named gap today. 069-02 AC8 pins it: the library does not copy the denylist; a forwarded event is stripped by core's own dispatch (tested against a real `createAirlock`), and the Alloy path's gap stays named, owned by the existing refinement-todo item (no new claim of coverage). |

     If a `core/` addition is ever chosen instead, it lands vendor-neutral on `main` first (`core/`, with its tests and contract change), then flows to the vendor branches by the fold flow, and this ADR is amended to name it exactly. None is chosen here.
   - **Optional forward to core.** When the page passes an `airlock` instance, an event push is also forwarded to `airlock.push({ event, ...params })`, so other connectors and the denylist see it. Only `event`, `xdm` and `data` are forwarded (never `configOverrides`). The Alloy connector subscribes to core `page_view`, so forwarding a `page_view` to an instance hosting Alloy would send twice: the forward skips events the Alloy connector subscribes to (a fixed list pinned by a test against `connectors/alloy/connector.js`), so the event is sent to Alloy once (069-02 AC8, tested with `page_view`).
   - **The opt-in migration proxy.** `installAdobeDataLayerProxy(options?)` is an explicit method on the library (not a `martechConfig` flag, so it is greppable, never set by defaulted config, and visibly not the standard path). It patches `push` on `window.adobeDataLayer` (or the given instance name) and forwards ACDL-shaped object pushes into the generic mechanism, after draining the entries already on the array. It is documented as a migration aid, not a best practice. The library never calls it. It carries the loss table below; the array instance is kept so earlier references stay valid, and `push` still appends to the array.
   - **What is lost against ACDL (proxy only) and what happens to each:**

     | ACDL feature | Disposition |
     |---|---|
     | Function pushes (`push(function (dl) {...})`) | Dropped, never executed: `datalayer-function-push-dropped`. Page code in the capture path is what AD-2 forbids. |
     | `addEventListener`, `removeEventListener`, `on`, `off` | Present on the proxy but register nothing, do not throw: `datalayer-listener-not-supported`. The listener `aem-martech` registers is replaced by the library's own event mapping. |
     | `adobeDataLayer:event` and `adobeDataLayer:change` notifications | Not emitted. |
     | `getState` returning a deep clone | A synchronous main-thread read of the live state by reference, per `contracts/push-api.md` (the send-time merge copies, so hooks cannot mutate it). A stock difference, with a test. |
     | `shouldProcessEvent(payload)`, `onBeforeEventSend` | Kept on the main thread, because a function cannot cross the airlock. They run in the drain, never inside `push`. A throwing one drops the event with `hook-threw`. |
     | A foreign ACDL on the array | The proxy does not install: `datalayer-foreign-implementation`. One that loads later and replaces `push` is detected at the next drain, with the same diagnostic. |
     | The eager-phase fallback in stock (a shallow merge of non-event entries before ACDL loads) | Not reproduced. The data layer folds as ACDL's `getState()` does at every phase. A stock difference owned by 069-02 AC5. |

     Every row has an owning AC in 069-02 (AC1 the generic mechanism, AC2 capture cost and drain, AC3 state and the hook copy, AC4 events and timing, AC5 the lost-feature rows and the eager fallback, AC6 the proxy install, AC7 blocks, AC8 forward and denylist, AC9 no capability and no global).
   - **Does the "no shipped global" rule extend to the data layer?** The rule is about `alloy`, because a page-callable `alloy` is a capability into the chamber. By default the library installs no data-layer global either. The generic data layer is reached through the library's functions, and the opt-in proxy is a capture surface plus a read-only state getter, with no capability: it reaches the chamber only through the library's fixed mapping. The library reads and writes no other global (069-02 AC9).
   - **The stock arm keeps real ACDL.** The differential's stock arm still loads real ACDL 3.0.1; the library arm loads none and uses no proxy (the journey pushes through `pushEventToDataLayer`), and its requests must still equal the recording and the stock run (069-03 AC1).

6. **Consent.** `updateUserConsent` goes through `handle.setAdobeConsent` and nothing else. The library never calls `handle.setConsent(vector)`, never derives a vector, and never reads Alloy's consent state: the seal's decision stays the vector `setAdobeConsent` derives from the same object (ADR-0064 point 1), so the object is data the chamber may send and never a signal the seal believes. A handle without `setAdobeConsent` (a composite or other handle) is rejected at creation with a plain Error, since silently falling back to the vector would drop `marketing` and `share` without the page knowing.

7. **The wrapper.** `createAlloyCommandBridge` stays as a lower-level, stock-shaped API for a site that has its own `alloy(command, options)` code and wants to own the global itself. It is not the `aem-martech` path any more. Its `applyPropositions` matches stock: a call without a non-empty `propositions` array renders nothing, sends nothing and resolves `{ propositions: [] }`, and the combined `{ propositions, viewName }` form still reaches the handle (Owner decision, 2026-11-23, verbatim: "Library renders, wrapper matches stock (Recommended)". The library's `applyPersonalization` calls the handle directly, so it still renders the bare form.) It otherwise receives no new parity work: it picks up the 069-01 handle additions only where they are free (its `sendEvent` resolves with the result when the handle offers `sendEvent`). Slice 064-31 is re-scoped against this.

8. **No `core/` change and no ADR-0063 allowlist change.** The three handle additions (`sendEvent`, `applyPropositions({ viewName })`, a settling `setAdobeConsent`) live in `adapters/eds/index.js` and, for the consent acknowledgement, the Alloy chamber's message handling under `connectors/alloy/`. They are not ADR-0063 commands (`handle.command` and its five-command allowlist are unchanged). If the slice finds it needs a `core/` change, it must be vendor-neutral and named in its Findings.

9. **The proof.** A third arm in the S10 B5 differential (`test/adobe-b5-martech.test.js`: real Chromium, pinned Alloy 2.31.1, the recorded S10 corpus, and the stock `aem-martech` run). The library's requests (order, paths, methods, hosts, bodies) equal the recording and the stock run, and `window.alloy` stays `undefined` in the page for the whole run. Hermetic tests cover each export in the map and the security-relevant rules (no global, consent only through `setAdobeConsent`, the seal deciding from the vector). The recording and the frozen corpus are the only inputs; no new live capture.

### Relation to the other ADRs

- ADR-0063: unchanged. The library reaches the five commands only through `handle.command` (via `getAirlockHandle`).
- ADR-0064: `updateUserConsent` is the first product caller of `setAdobeConsent`.
- ADR-0062: the consent hold, the endpoint ceiling and the config pin are untouched. `defaultConsent: "in"` is not honoured so the library cannot grant before the page's consent call.
- ADR-0017: the library ships experimental; freezing it is a later ADR.
- ADR-0002 and AD-2, AD-3 (`contracts/push-api.md`): the data layer is the thin capture layer. The generic data layer's push is O(1) in the state size (validate and append, no merge), the state is Airlock's reducer folded lazily, and no page function runs inside `push`.

## Consequences

**Becomes easier:**
- An Adobe EDS site moves off the main-thread Alloy and off ACDL by changing one import and adding one boot option block. No `alloy` global exists, and the data layer is Airlock's generic mechanism; a site that must keep pushing to `adobeDataLayer` calls `installAdobeDataLayerProxy()` as a migration step.
- The proof is one differential against the real stock library, not a description of it.

**Becomes harder:**
- A second surface to keep in step with `aem-martech` releases. The pin (1aa3dee3) and the third arm of the differential catch drift only when the pin is moved on purpose.
- Sites that call `window.alloy` directly must change those calls. This is deliberate.
- Sites that use ACDL function pushes or listeners get diagnostics and lose those behaviors (point 5's table). A site that loads its own ACDL is not replaced. `window.adobeDataLayer` is not there unless the site opts in.
- We own a data-layer reducer that must keep matching ACDL's `getState()` for the pushes `aem-martech` sites make, and a migration proxy we would like to retire.
- `martechDelayed` does not load Launch containers; a site that needs one stays on its own loader until a Launch decision exists.
- The handle gains three adapter methods the wrapper and the library share.

**Not changed:**
- `core/`, the ADR-0063 allowlist, the endpoint ceiling, the consent hold and the 068 opt-out.
- The wrapper's existing behavior.

## Assumptions

- `aem-martech` 1aa3dee3 `src/index.js` exports exactly the 14 names above (read from the pinned file on 2026-11-21).
- Alloy 2.31.1's `applyPropositions` accepts `viewName` only together with non-empty `propositions` (read from the `@adobe/alloy@2.31.1` tag: `createApplyPropositions.js`). The first version of this assumption said the bare form renders the view cache; it does not (amended 2026-11-22).
- The interact response's `propositions` and `decisions` can be collected per event inside the adapter from the deliveries the event produces. The adapter already tracks them per event (`noteAttempts`, `settleDeliveries`, the view cache). Slice 069-01 proves this: the recorded S10 interact answer proves only the empty case (it carries no propositions or decisions); the proposition-bearing proof uses a synthetic answer (see the 069-01 deviation log). If it cannot, the slice reports `blocked` and the ADR is revisited.
- `onBeforeEventSend` can be given the same `xdm` stock passes it (context merged in) on the main thread, and hook edits to context fields survive the chamber's own Alloy context merge. This is 064-31 AC3's open question and is proven in 069-01.
- A silent chamber must not leave `updateUserConsent` pending forever: the settling `setAdobeConsent` is bounded by a timeout and settles on dispose (069-01 AC5).

- Airlock's generic data layer can carry state pushes and the event mapping in an adapter module with no `core/` change (point 5's gap table); the S10 journey needs no `adobeDataLayer` proxy because it pushes through `pushEventToDataLayer` (verified in `test/adobe-b5-martech.test.js`). ACDL 3.0.1's `getState()` on the corpus of pushes `aem-martech` sites make can be matched by a small deep-merge reducer. Slice 069-02 AC3 proves it in real Chromium with both side by side; a difference that cannot be matched is dropped with a diagnostic and a test, never left as a note.
- Validate-and-append is cheap enough for the interaction path, and the lazy fold plus the per-send O(state) copy are acceptable in a separate task. 069-02 AC2 and AC3 pin the push cost with a visit counter and record the send cost on the S10 state.

## Kill criteria

- The S10 differential's third arm cannot match the stock run without a `core/` change or an allowlist change: stop and bring it back.
- Per-event interact results cannot be built in the adapter without trusting the chamber's own word about what egress happened.
- The reducer cannot match ACDL's `getState()` on the corpus without running page callbacks in `push`: stop and bring it back.
- The generic data layer needs a `core/` change to carry the journey: stop, amend this ADR to name it, and land it on `main` first.

## Open questions

None beyond acceptance. The owner picked Option A. The proxy is an explicit `installAdobeDataLayerProxy()` method rather than a config flag, so it is greppable and never reached by a defaulted option; say so at acceptance if a flag is preferred.
