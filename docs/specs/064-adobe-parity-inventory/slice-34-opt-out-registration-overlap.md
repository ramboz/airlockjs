## Slice 064-34 — an opt-out in flight for a superseded consent update still forwards

**Goal:** A refusal the chamber sends for a consent update that a newer update has already replaced is not held, so a quick sequence of updates records at Adobe as stock does, with no widening of what the chamber may put on the wire.

**DoR:**
- ✅ 064-33 built (the adapter registers the object and the vector; core's `expectOptOutConsent` replaces the registration on each call).
- ✅ 068-03 built (`host.expectOptOutConsent`, the checked forward).

**Acceptance Criteria:**

1. When the page updates consent twice in one tick (`setAdobeConsent` then `setConsent`, or two `setAdobeConsent` calls), the chamber's set-consent request for the first update still forwards and the newer one does too, while a value that was never registered is still held. Shown by a hermetic test that fails on the 064-33 code (the first request is held).
2. A real-Chromium check, behind `describe.runIf(process.env.AIRLOCK_REAL_CHROMIUM === "1")` with a GATING step in the `browser-oracle` job, shows the refusal Alloy puts on the wire for the page's Adobe 2.0 object equals the registered object, using a SYNTHETIC response (stop and report `blocked` if a new live capture is needed).

**DoD:**
- `npm test && npm run lint` and servo gate pass.

**Anti-horizontal-phasing check:** Vertical: two quick consent updates through the chamber to both forwarded requests on the wire.

## Findings

**Design.** The registration logic is adapter-only and stays on vendor-adobe; core still stores one replaced registration. The only core change is the vendor-neutral timeout hook 068-04, landed on main first (rounds 1 to 4 had no core change). Every consent update (`setConsent`, `setAdobeConsent`) adds a *generation*: the page's object (if one was posted) plus the vector-shaped consent; an update identical to the last update (remembered even after its generation was consumed) adds none. The host registration is the flattened union of the live generations, passed to core's replacing `expectOptOutConsent`. **Lifetime is request-correlated, against Alloy 2.31.1's own behaviour** (read from the pinned bundle and confirmed in real Chromium): `setConsent` runs through a serialized task queue, so requests leave in order, and a request is sent only when the consent differs from the last one stored (a repeated identical consent sends none; an object Alloy rejects sends none and the chamber's vector retry is the request). So when a request reaches `dispatch` (only after the host gates pass), the oldest generation holding its `consent` (key-order-free) and every older generation are consumed. A value already sent is held when replayed, unless its request failed or the host timed it out, in which case that request's own generation is restored once (below). There is no timer and no cap; every registered value is one the page gave, and the host forwards an opt-out only while consent is denied, so a value no update produced is still held.

**AC1 (hermetic, `test/alloy-adobe-consent.test.js`, describe "064-34").** "setAdobeConsent then setConsent" and "two setAdobeConsent calls" fail on the 064-33 code (the first request is held) and pass now; a never-registered value is held in both. Further tests: retirement once a newer update's request has left; a key-reordered request matches and retires; a value repeated in a later update does not retire one still in flight; a value whose request succeeded is held when replayed (a failed request restores its generation, below), and a later update still adds; the same update given again after its request left adds nothing; **post-settlement**: 25 cycles of A/B each forward exactly once and a replay of both afterwards is held (the registration does not grow). The chain is: hermetic tests show what is registered is the page's object; the real-Chromium test shows what reaches the wire is that object. It does not read the registration directly.

The 064-33 retry test now sends the vector alone: the retry exists only when Alloy rejected the object, which sends no object request. (2) The 068-03 AC4 re-register test in `test/opt-out-consent-registration.test.js` expects accumulation on vendor-adobe; core's replace semantics are unchanged, so this file may conflict when main next changes it. **First-pass residuals (still true except where marked).** An update whose request never leaves (a rejected object whose retry never comes, a refusal the page withdrew, or a chamber that sends nothing) keeps its generation until a later request consumes it; each new distinct update adds one generation, so with no request reaching `dispatch` at all the list grows by the page's own distinct updates, and the next request that gets through clears everything up to its match; there is no timer or cap, and it never lets a value the page did not give through. (Superseded: Alloy does not store a failed consent, so a held repeat was a regression, repaired in round 4 below.) Accepted edge: a vector retry that arrives after a newer update's request has consumed its generation is held, which matches stock's final state (the older value would overwrite the newer). The vector retry after a rejected object followed by the same vector again as a later update can also linger (Alloy stored it already), bounded to that one generation. A compromised chamber can send such a not-yet-consumed page value while consent is denied. Consumption assumes Alloy sends consent requests in order, which its task queue guarantees; the oldest-match rule errs toward keeping registrations.

**Failure-repeat regression (found after the round-3 passes; slice reopened, repaired in the owner-approved round 4).** The repeat skip (`lastUpdateKey`) assumed Alloy also treats a repeat of a failed update as nothing to send. Pinned Alloy 2.31.1 does not: `setConsent` runs `lookup(consent)`, then `addTask(() => isNew() ? send : resolve).then(() => s.save())`, and `save()` (the consentHashes write) runs only after the request resolves, so a network failure or non-2xx answer (Alloy throws) stores nothing. Alloy's own retry covers only HTTP 429/502/503/504 (up to 3 attempts, same sender, before the outcome); a rejected fetch is thrown with no retry on this path. **Correction of the first probe:** the earlier real-Chromium note (one aborted POST, then 2 POSTs) was flawed: after a network failure Alloy retries once on its OTHER host, and that fallback, not the page's repeat, was the second POST. The repeat claim rests on the pinned source above and on the non-ok case, shown in real Chromium (SYNTHETIC): first request answered 500, then the same refusal set twice gave 2 set-consent POSTs in stock. Our adapter consumed the generation at dispatch and `lastUpdateKey` then skips the page's repeat, so Alloy's repeat request is held: a legitimate retry is dropped. Introduced by this slice's `lastUpdateKey` (c258caed); not an accepted residual. Probe script kept in the session artifacts, not the repo.

**Fix.** `retireOptOutGenerations` returns the generation it consumed; when that request then fails (rejected fetch, or `res.ok === false`) the dispatch puts exactly that generation back at the front (`restoreAfterFailure`, by identity, once) and re-registers. Alloy's fallback to its other host and the page's identical repeat both send the same consent again and match it, then consume it again on success, so retention stays request-correlated with no timer or cap. A failed request for an older update restores only its own generation: a newer update's value is still consumed when sent and held when replayed. The registered value is the request's one consent and the generation is matched by value, so the object/vector correlation is the one `retireOptOutGenerations` already used.

**Round 6 fix.** Round 5's craft review found that `restoreOnce` ran only for a rejected fetch or `res.ok === false`; a throw from `res.text()`, the headers read or `cacheViewPropositions` on an ok answer rejects `dispatch`, Alloy sees a failure and stores nothing, yet the generation stayed consumed. Every rejection of the dispatch body now restores the same generation at most once (the same `restoreOnce`) and rethrows the original error, so the observable failure is unchanged. Tests: "an ok answer whose body read throws" and "... header read throws" run through the failures table (repeat forwards, further repeat held, Alloy's own resend forwards once); removing the new catch fails 4.
