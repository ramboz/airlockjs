## Slice 064-32 — first push query edge cases match stock

**Goal:** The decision of whether a push carries a personalization query, and what it carries, matches pinned stock Alloy 2.31.1 for the odd inputs 064-29 left out: invalid surfaces and scopes, placement scopes spent by `applyResponse`, a notification-shaped push that passes scopes, and the order of a push against an `applyResponse` call.

**DoR:**
- ✅ 064-29 done (the host tells the chamber the view cache is warm; `carriesQuery` follows stock for well-formed scopes and surfaces).

**Acceptance Criteria:**

1. (Amended by the owner, 2026-11-25; see Findings.) A push whose `personalization.surfaces` is a non-empty array sends the personalization query even when stock drops every entry as invalid (not `web://...` or `#...`), and the query carries the surfaces stock keeps (none, then). A cache-only answer, with no fetch, applies only to empty or absent surfaces, subject to scopes and default selectors. Shown by a differential test on the request bodies and the DOM. The original text said stock answers from the cache without a fetch; the pinned 2.31.1 bundle shows that is false.
2. A push whose `decisionScopes` holds an empty string or a non-string entry behaves as stock for the same call (a query, or the validation error stock raises), shown by a differential test on the request bodies and the settled result.
3. A push whose XDM names a `decisioning.proposition*` event type and passes `decisionScopes` sends the personalization query as stock does (today the connector sends none, 064-20), shown by a differential test on the request body.
4. A boot with `placements` naming scopes other than `__view__`, then `applyResponse`, then a first push that passes no scopes: the placements' scopes are not fetched (stock declares none and sends no query on a warm cache), shown by a differential test on the request bodies; the adopter docs say an earlier `applyResponse` spends the declared placement scopes.
5. (Clause b amended by the owner, round 5; see Findings.) A push enqueued before an `applyResponse` call, and still waiting when that call finishes, does not see its cache (stock runs the push first, with the declared scopes and a cold cache), and the order of a push against the redirect display of an `applyResponse` that came before it matches stock per call pattern (original wording: "an event pushed after an `applyResponse` never reaches the wire ahead of that response's redirect display", which pinned stock contradicts when the apply is not awaited), shown by a differential test on the request order. Today the host reads the cache state when an event runs, not in call order.

**Owner decision on AC1 (2026-11-25).** The first run of the differential showed AC1's premise was wrong. In stock, `shouldFetchData` is `hasScopes() || hasSurfaces() || shouldRequestDefaultPersonalization()`, and `hasSurfaces` is a raw non-empty-array check. Entries are filtered only later, so an all-invalid or empty-string surfaces array still sends a query (with `surfaces: []`). Airlock already sent that query. The owner approved correcting the AC to match stock ("Approve the stock-matching correction (Recommended)"), kept the request-body and DOM comparison, and left the other ACs unchanged. The original wording is kept in the amended criterion above. The decision and the differential's evidence are in the coordinator's session record, not in this repo.

- **AC1.** The host's `carriesQuery` and the chamber now share one rule, `carriesPersonalizationQuery` (`connectors/alloy/connector.js`): a raw non-empty array of scopes or surfaces, an explicit default `true`, or a value that is not an array (so Alloy rejects it, as stock does). Test: "AC1 (owner-amended)" in `test/adobe-b4-personalization.test.js`.
- **AC2.** A scope list with an empty, non-string or repeated entry goes to Alloy as given, boot scopes after the page's own so the index in the error stays stock's. `""` and `null` query, `[1]`, `"x"` and `["a","a"]` reject with stock's message (the namespace prefix differs, `[alloy]` against `[stockAlloy]`, and the test normalizes only that). Well-formed lists are merged as before. Surfaces now go through as given too. This replaces 064-21's silent drop of non-string surfaces and its dedupe of repeated scopes: both differ from stock, which rejects them. Tests: "AC2" plus the connector tests.
- **AC3.** A `decisioning.proposition*` push that passes scopes, surfaces or an explicit default is a query: no boot scopes, `sendDisplayEvent: false`. A notification with no query input is unchanged. Test: "AC3", warm and cold. Still open: such a push does not deliver its decisions to the page.
- **AC4.** Already matched stock, so no code change; the differential is the proof. Test: "AC4". The adopter note (an earlier `applyResponse` spends the declared placement scopes) is in the `placements` option JSDoc, ADR-0063 and the CHANGELOG.
- **AC5.** a) A push now takes its cache warmth from call order: it is warm only if the cache was initialized when it was called, or an apply in flight at that time succeeded, or an earlier push fetched. Before, it read the cache when it ran. The differential uses a push rejected by option validation (no request, no scopes spent) as the slow predecessor. Hermetic: "AC5: a push queued before an applyResponse call runs cold ...". b) Round 4 added a real stock-versus-chamber differential. The redirect navigation is intercepted with `page.route(url, r => r.abort("aborted"))`, which keeps the page context alive, and the edge requests are traced from the Playwright side. With the apply awaited, both stock and ours send the display, then the push; the test asserts that order and that both navigate. Round 4 also removed the drain's extra front check from round 1: with it deleted, the differential and the 064-29 hermetic test stay green, so no test showed it was reachable. c) Round 4 fixed two call-order gaps found in review. A boot with no declared scopes now sends the default view query when the push was called before an apply (the host sends `viewCacheCold`, and the chamber turns it into `defaultPersonalizationEnabled`). A failed apply no longer warms a push called behind it when a later apply succeeds. Both have red-to-green differentials.
- **Red to green.** With the production change reverted: AC1, AC2, AC3 and AC5 fail in real Chromium (AC4 already passed), and the hermetic AC5 test fails (p1 reads warm). All pass with it.
- **Finding (round 4, unawaited apply; resolved in round 5):** when the apply is not awaited and a push is called right after it, stock sends the push first, then the redirect display. Ours holds the push behind the display (the 064-29 gate). Observed stock `[pageViews, display]`, ours `[display, pageViews]`. For an awaited apply both agree on display then push, but stock navigates after the push and ours navigates before it. AC5 b is covered for the awaited case only. Round 4 left it for an owner decision.
- **Round 5 (owner: "Match stock and authorize one bounded corrective round (Recommended)").** a) *Order policy.* The host gate now waits for an in-flight apply's view cache warm (a `warmed` hook right after the apply is applied), not for its render and redirect display. Observed request traces, real Chromium, stock against ours, redirect scope `__view__`: unawaited apply then push, stock and ours both `[pageViews, display, navigate]`; awaited apply then push, stock `[display, pageViews, navigate]`. Both patterns also run with a real navigation (the target fulfilled with a stub page, not aborted) and give the same traces as the aborted runs. b) *Navigation timing.* For the awaited case ours starts the navigation before the push request (`[display, navigate, pageViews]`) in every run. Stock usually navigates after the push, but a repeat run under CPU load showed stock itself navigating first, so its navigation order is a race. The push request starts in both arms in every run, so nothing is lost. The test pins the edge events and that both navigate, and not the navigation order for that case. A full-suite run then caught the push request missing in our arm (the page navigated before the worker hop issued it), where stock had sent it. So the renderer now holds the navigation after the display is sent: one macrotask, then, only when page events are still waiting, until the next edge request is issued, bounded to 250 ms (`navigationGate`, `NAVIGATION_GATE_MS`). The loss was intermittent and could not be reproduced on demand, so there is no red-to-green for this gate; the evidence is the failing full-suite run and green repeats under CPU load after it. The navigation-order difference is not otherwise claimed as matched. c) *Cache timing race.* The cold hint no longer reads the host's `isInitialized()` when the push runs. The host counts applies issued (`appliesIssued`): a push is cold when it was called before an apply that was issued later and no warming apply ran first. Sending the hint when the chamber is truly cold is harmless. d) *Own scopes.* A cold push that passes its own scopes also queries `__view__` in stock (differential "AC5 (round 5)", red before the connector change, which dropped the hint when the call carried a query); the connector now keeps the hint unless the page passes an explicit `defaultPersonalizationEnabled`. e) *Recorded limit.* An apply that warms the cache but fails to render counts as warm, as in stock. f) The hermetic AC5 test also asserts the `viewCacheCold` flags. The differential trace wait grew to 4 s because a full-suite run under load missed the push in one run.
