## Slice 069-03 — `adapters/eds/martech.js`: the `aem-martech` exports on the `bootAlloy` handle

**Goal:** An Adobe EDS site swaps its `aem-martech` import for the Airlock library and the S10 journey sends the same requests, with no `window.alloy` anywhere.

**DoR:**
- ✅ 064-21, 064-29, 064-30 done.
- ✅ ADR-0065 Accepted by the owner (2026-11-22).
- ⬜ 069-01 and 069-02 done.

**Acceptance Criteria:**

1. The library's S10 requests (order, paths, methods, hosts and bodies) equal the recording and the stock `aem-martech` run, shown by a third arm in `test/adobe-b5-martech.test.js` (real Chromium, pinned Alloy 2.31.1, the recorded S10 corpus). The collect bodies are compared against the stock run only (they were never recorded; the test name says SYNTHETIC). The stock arm keeps its real ACDL 3.0.1; the library arm loads no ACDL (no `acdl.min.js` request), does not call `installAdobeDataLayerProxy()` (the journey's link event goes through `pushEventToDataLayer`, which is the generic data layer), and `window.adobeDataLayer` stays undefined in it.
2. No page global: the library never reads or writes `window.alloy`, `window.__alloyNS` or `window[alloyInstanceName]`, and never imports `alloy.min.js` on the main thread. Shown by (a) a hermetic test with a global proxy that fails on any access of those names from creation through a full `initMartech` / `martechEager` / `martechLazy` / `updateUserConsent` run, and (b) the real-Chromium arm asserting `window.alloy === undefined` and no `alloy.min.js` request on the main thread, throughout the journey. `alloyInstanceName` other than `"alloy"` gets an `unsupported-option` diagnostic, and `dataLayerInstanceName` (inert unless the proxy is installed) set to `alloy`, `__alloyNS` or the `alloyInstanceName` value is rejected with a plain Error by the proxy install; this slice owns that check (069-02's `FORBIDDEN_INSTANCE_NAMES` has only `alloy` and `__alloyNS`) with a test of each of the three names.
3. `updateUserConsent` reaches Alloy through `handle.setAdobeConsent` only, and the seal still decides from the vector: hermetic tests that (a) the object equals what `aem-martech` builds for `marketing` as boolean and object, `collect`, `personalize`, `share`; (b) the library never calls `handle.setConsent`; (c) `collect: false` never yields a granted `analytics_storage` at the seal, whatever the chamber does with the object; (d) a handle without `setAdobeConsent` is rejected at creation with a plain Error; (e) a call before the chamber is configured is queued and settles with Alloy's outcome (069-01 AC5); (f) `martechConfig.airlock` keys other than `bundleUrl` and `workerUrl`, notably `consent` and `consentHold`, are rejected; (g) `defaultConsent: "out"` sends no request and drops events until a grant, matching the stock run in real Chromium, and `"in"` never grants before `updateUserConsent`.
4. Every export in ADR-0065's map has a test, or is listed as dropped or different with a reason and a test of the difference: `DEFAULT_CONFIG` (same keys and values as the pinned file), `initMartech` (validation errors, boot options mapping, `defaultConsent: "in"` not honoured with a diagnostic, `idMigrationEnabled` and other options diagnosed, `context` default, `onBeforeEventSend` stripped before `bootAlloy`, boot timing, and the pre-boot queue replaying `sendEvent`, `getPersonalizationForView`, `applyPersonalization` and `updateUserConsent` in order, interleaved with the data layer's events in push order (069-02 AC2's shared-queue clause: a test pushes data-layer events between those calls before boot; direct calls share 069-02's 200-entry pre-attach cap, so the test states the eviction behavior and whether the caller's promise settles)), `sendEvent`, `sendAnalyticsEvent` (non-empty `edgeConfigOverrides` diagnosed, `{}` dropped; this is 064-31 AC7's disposition, recorded against ADR-0062's config-pin rule), `pushToDataLayer`, `pushEventToDataLayer`, `updateUserConsent`, `initRumTracking` (`withRumEnhancer` dropped with a diagnostic), `isPersonalizationEnabled`, `getPersonalizationForView`, `applyPersonalization`, `martechEager`, `martechLazy`, `martechDelayed` (a non-empty `launchUrls` is not loaded and gets a `launch-not-loaded` diagnostic per URL, no request), and the extra `getAirlockHandle` (returns the `bootAlloy` handle once it exists, throws before, and reaches `command("getIdentity")`). There is no `dataLayerUrl` key; the library-only `martechConfig` keys are `airlock` and `handle`. Differences owned here, each with a test of the difference: (a) `applyPersonalization(viewName)` renders the cached view (the bare `handle.applyPropositions({ viewName })`), while stock `aem-martech` 2.31.1 is a no-op for the bare form (its validator rejects it and it resolves `{ propositions: [] }`), shown by a test that both forms are exercised and only the combined `{ propositions, viewName }` form is compared with stock in real Chromium; (b) `sendEvent` resolves `propositions` and `decisions` equal to stock's and `{}` for the rest (stock's destinations and the like are not carried), pinned by a test; `updateUserConsent` resolves `{}`, which stock's `setConsent` also resolved in the real-Chromium run (069-01 AC5), so no difference is claimed for it; (c) the `setAdobeConsent` 10 s timeout and its kind-"none" rejection carry Airlock's own messages, pinned by a test of each message, and a fallback-kind object (not postable) settles at once with `{}` because there is no Alloy outcome for the vector-shaped call, pinned by a test; (d) the wrapper's `sendEvent` rejects on a throwing `onBeforeEventSend` as stock does (069-01 deviation log), through the library's `sendEvent` as well; (e) a partly rendered proposition is marked `renderAttempted` as a whole; (f) `timestamp` and `placeContext.localTime` are sampled on the main thread, pinned by a test that the hook sees them; (g) a page hook that deletes a context field gets it refilled by the chamber's Alloy context merge, where stock sends the event without it, pinned by a test of the difference.
5. The data layer follows ADR-0065 point 5 through the 069-02 generic data layer: `initMartech` creates it (unless `dataLayer: false`, where none is created and `pushToDataLayer` throws stock's error), `martechLazy` scans the blocks through it, `pushToDataLayer` and `pushEventToDataLayer` push into it, `includeDataLayerState` merges its state into `xdm` at send (state overriding, as stock), and its events go to `sendAnalyticsEvent` with `shouldProcessEvent` and `onBeforeEventSend` run on the main thread in the drain. The library exposes `installAdobeDataLayerProxy` (069-02 AC6) and never calls it. Shown in real Chromium by the journey's link event (requests equal the stock arm's with real ACDL, no `acdl.min.js` request, `window.adobeDataLayer` undefined) and a hermetic test that `initMartech`, `martechEager` and `martechLazy` never touch it, plus a measurement of the S10 state-carrying send cost with `includeDataLayerState` (069-02 AC3 left it here), recorded in Findings, replacing 069-02's stand-in test (a full run leaves `window.adobeDataLayer` untouched, from 069-02 AC6); with `dataLayer: false`, `pushToDataLayer` throws stock's error (from 069-02 AC9, tested); the data-layer differences are owned by 069-02 AC3, AC5 and AC8, not here.
6. The page-view and display flows match the stock run's requests in real Chromium: the default path (page view from `martechEager`'s `finally`, none from `martechLazy`), personalization off, `performanceOptimized: false` (one `__view__` fetch with a timeout, body hidden then restored), `trackPageView: false` (`decisioning.propositionDisplay`) and a late display after the timeout; the S10 no-offer case, and a synthetic offer answer (SYNTHETIC, the 064-20 sense) renders and reports the same displays as stock, checking `renderDecisions: true` against what stock renders (real Chromium). `datasetId` is dropped with a diagnostic (the config pin forbids carrying it), and `type` versus `xdm.eventType` precedence follows stock (`type: 'decisioning.propositionFetch'`; the wrapper's `xdm.eventType` priority is unchanged).
7. `configure` conflicts and unsupported `webSDKConfig` options get an `unsupported-option` diagnostic on the library's `onDiagnostic`, never silently (064-31 AC6 moved here, re-expressed: `webSDKConfig` is the source of the boot options, so the conflict is an option the library cannot carry); the options the journey passes that stay inert (`debugEnabled`, `targetMigrationEnabled`, `autoCollectPropositionInteractions`) are named in the library header. A page `__view__` scope on a first call with named boot scopes sends the scopes live Alloy sends (stock's `__view__` suppression), or a diagnostic names the difference (064-31 AC7, third item).
8. `createAlloyCommandBridge` is unchanged in behavior and kept as the lower-level API: the 064-21 wrapper-arm tests stay green, and the third arm is added beside them, not instead.
9. The Apache-2.0 notice for `adobe-rnd/aem-martech` is in the library header and in a new `THIRD_PARTY_NOTICES.md` at the repository root created by this slice (a hermetic test that the header carries it and the file names `adobe-rnd/aem-martech`); no `core/` change; the ADR-0063 allowlist tests stay green.
10. The migration note (stock `alloy("command")` to the library or `getAirlockHandle().command`) is in the Findings and `docs/architecture.md` names the new module boundary.
