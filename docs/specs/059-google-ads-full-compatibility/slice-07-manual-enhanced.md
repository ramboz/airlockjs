## Slice 059-07 - Manual enhanced matching journeys

**Goal:** An adopter supplies permitted first-party conversion data and preserves
native normalization, hashes and order associations through governed delivery.

**DoR:**
- [ ] 059-06 is DONE; C1-C3/058 cover raw/prehashed value semantics and all
      associated request/response/state branches.
- [ ] Parent verifies destination customer-data terms, eligibility and current
      unified enhanced-conversion account/action settings; no enhanced-data
      activation or real identity send is authorized by this draft.
- [ ] Pin per-field normalization, eligible key combinations, array limits,
      clearing/retention and actual native precedence. Synthetic local vectors
      and any later legitimate matching inputs are explicitly supplied privately.
- [ ] Pin the product matching/outcome evidence method before claiming efficacy;
      a synthetic hash-shaped request is not matching proof.

**Acceptance Criteria:**

1. Manual user_data raw email, phone and supported name/address combinations
   follow native eligibility, string/omission/invalid behavior. Support documented
   multiple email/phone/address values and actual native bounds; never stringify
   missing input into plausible personal data.
2. Raw normalization covers trimming/case, Gmail/Googlemail local-part dots,
   E.164 phone format and field-specific address rules as actually pinned.
   Hash only the required fields using the native-equivalent algorithm and
   encoding; do not assume every address field is hashed.
3. Prehashed email/phone/name keys are not hashed again. Raw and correctly
   prehashed equivalents yield equal full permitted values where native requires
   that relation; distinct controls remain unequal and array identities/order
   stay associated. All comparisons precede privacy redaction.
4. Correct user data joins the intended order/event/destination at native
   collection/dispatch time. Delayed, stale, previous-customer, cleared, repeated
   and multiple-conversion inputs cannot leak or attach to the wrong conversion.
5. Terms not accepted, disabled account/action, ad_user_data denied and
   independently denied storage/personalization preserve native suppression/
   measurement behavior with governed policy enforcement. Source identities
   leave only through the exact fields/transformations permitted by the reviewed
   native contract and policy; no broad personal-data grant or incidental leak.
6. C1 includes enhanced-data destinations/fields, all response branches,
   session/cookie association and actual worker hashing/state ownership.
   An em prefix or field presence alone cannot establish a nonempty correct hash,
   complete sequence, account acceptance or matching.
7. Double hash, altered normalization/input, collapsed identities, wrong order,
   stale data, extra destination and denied-user-data mutations all fail.
   Legitimate owned product observations distinguish receipt, matching and
   attribution; inaccessible matching evidence stays blocked, not assumed.
8. Operator output offers precise private correlation plus sanitized diagnostics
   and retention/clearing controls. Complete raw and prehashed paths meet C3 and
   the frozen boundary, with no logs or committed fixtures exposing personal values.
